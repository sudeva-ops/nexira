# Proposed schema changes

Changes to `docs/schema/nexira_schema.sql` (v0.2) that are **proposed, not approved**. Nothing here goes into a migration until a human approves it, and changes to RLS or grants also need a D-29 sign-off. Once approved, each change ships as a new Alembic migration; migration 0001 is never edited.

| ID | Status | Change | Why | Source |
|---|---|---|---|---|
| PC-01 | Proposed | `list_tenant_ids()` — `SECURITY DEFINER`, returns `SETOF uuid` from `tenant`, `EXECUTE` granted to `nexira_app` only | Background jobs (proposal expiry, check-in escalation) have no token, so they cannot discover tenants. D-04 allows only `resolve_tenant_by_issuer` as a cross-tenant read, so this needs a decision. Phase 1 uses `WORKER_TENANT_IDS` from config instead. | plan G-01, Q6 |
| PC-02 | Proposed | `action_policy.undo_window_s integer NOT NULL DEFAULT 300 CHECK (undo_window_s > 0)` | The undo window for level 1 is not defined anywhere. Phase 1 uses the `UNDO_WINDOW_S` config value. | plan G-17, Q7 |
| PC-03 | Proposed. Migration 0002 used explicit grants instead, so this stays open for future tables | In the migration that adds the first new table: `ALTER DEFAULT PRIVILEGES FOR ROLE nexira_owner IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO nexira_app` (and the same for sequences) | v0.2 grants `ON ALL TABLES` only once, so tables created later would have no runtime grants. The alternative is explicit grants in every migration. Either way, the catalogue test `test_every_tenant_table_forces_rls_with_tenant_policy` catches a missing RLS policy. | plan G-02 |
| PC-04 | Proposed | Make `next_reference()` `SECURITY DEFINER` (with `SET search_path`), then `REVOKE INSERT, UPDATE, DELETE ON reference_counter FROM nexira_app` | Today `nexira_api` can `UPDATE reference_counter SET last_value = …` in its own tenant. Unique keys on `reference` stop duplicates, but the next inserts would fail. Found in the Prompt 2 security check. | D-18 |
| PC-05 | Proposed | Block `DELETE` on `proposal_approval` (trigger or revoke), and block `INSERT` of extra steps after the proposal row exists | `nexira_app` can delete an undecided approval row, or add one. Found in the Prompt 2 security check. | D-16 |
| PC-06 | Proposed | `CREATE UNIQUE INDEX playbook_run_step_distinct_approver_uq ON playbook_run_step (run_id, approved_by) WHERE approved_by IS NOT NULL`, plus a trigger that allows setting `approved_by` only while the step is `AWAITING_APPROVAL` and never changing it afterwards | Playbook gates have no database backstop for D-16 (one person, one step) or for decided-once. Today `approvals.decide()` enforces both, with the run row locked, and that is the only enforcement. `proposal_approval` already has the equivalent index and triggers. Found in the independent review of Prompt 9. | D-16, plan G-08 |
| PC-07 | **Approved** 2026-10-25 by the product owner (PR #16; D-31). **Applied** in migration 0002 (Prompt 18, 🔒), with three tightenings: `UNIQUE NULLS NOT DISTINCT` (otherwise generic templates, whose mission is NULL, could repeat a code); a CHECK that `texts` is an object with `en`; a CHECK that `reviewed` is an object, default `{}` | `message_template` table: `id`, `tenant_id`, `code`, `kind` (`ALERT`, `ADVISORY`, `CHECKIN`), `mission_id` (NULL = generic), `name`, `texts jsonb` (`{"en": …, "ar": …}`), `reviewed jsonb` (`{"ar": false, …}`), `is_active`, `created_at`, `updated_at`; `UNIQUE (tenant_id, code, mission_id)`. FORCE RLS with `tenant_isolation`; SELECT, INSERT and UPDATE for `nexira_app` (no DELETE: deactivate instead). | Per-mission templates (MN-03). The PB-07 advisory text is fixed to Nairobi today, so a Paris incident gets a Nairobi advisory. | requirements-pilot.md MN-03, MN-04 |
| PC-08 | **Approved** 2026-10-25 by the product owner (PR #16; D-31). **Applied** in migration 0002 (Prompt 18, 🔒), with two tightenings: the trigger also runs on INSERT, and it also refuses `approved_by = submitted_by`. The review of Prompt 18 found gaps, closed by PC-10 | `notification_campaign`: add status `PENDING_APPROVAL` to the CHECK; add `template_id uuid REFERENCES message_template`, `submitted_by uuid`, `approved_by uuid`, `approved_at timestamptz`, `rejection_reason text`. Add a trigger refusing `approved_by = created_by` (when `created_by_type = 'USER'`) and any change to `approved_by` once it is set. | The second-person rule for citizen campaigns (MN-05), with a database backstop, as `proposal_approval` has for D-16. | requirements-pilot.md MN-05 |
| PC-10 | **Approved** 2026-10-25 by the product owner. **Applied** in migration 0002 (Prompt 18, 🔒), before 0002 was merged | Harden `notification_campaign_approval_guard`: (1) refuse any change to `created_by` or `created_by_type`, and to `submitted_by` once it is set; (2) compare `approved_by` with `created_by` as a uuid, not as text; (3) set `approved_by` only from status `PENDING_APPROVAL`, and never on INSERT; (4) refuse any change to `approved_at` once it is set; (5) `CHECK (status <> 'PENDING_APPROVAL' OR submitted_by IS NOT NULL)`; (6) `REVOKE DELETE ON notification_campaign FROM nexira_app` (no code deletes campaigns, and deleting one cascades to its deliveries and check-in answers). | The PC-08 backstop compares only the new values, and `nexira_app` can UPDATE the author columns. In the same UPDATE, someone can rewrite the author and approve their own campaign, approve a DRAFT, or insert a campaign that is already approved. Found by the independent review of Prompt 18. | D-31, MN-05 |
| PC-11 | **Approved** 2026-10-25 by the product owner. **Applied** in migration 0002 (Prompt 18, 🔒), before 0002 was merged | (1) Freeze a campaign's content (`campaign_type`, `message`, `translations`, `channels`, `audience_filter`, `template_id`, `incident_id`) once it leaves DRAFT. `escalate_after_s` stays adjustable for the check-in clock. (2) Approving moves the campaign to SENDING in the same statement, so an approved campaign is never DRAFT or PENDING_APPROVAL; a rejection returns it to DRAFT only while it is unapproved. (3) `CHECK ((approved_by IS NULL) = (approved_at IS NULL))`, and the trigger sets `approved_at := now()` when the approval is recorded. (4) `REVOKE DELETE ON notification_delivery, checkin_response FROM nexira_app`. | PC-10 bound the approval to a person but not to the content: the message or the audience could change while pending or after approval, so an approver could be shown one text while another was sent. Found by the re-review of Prompt 18. | D-31, MN-05 |
| PC-12 | **Approved** 2026-10-25 by the product owner. **Applied** in migration 0002 (Prompt 18, 🔒), before 0002 was merged | (1) **Forward-only status:** DRAFT → PENDING_APPROVAL, SENDING or CANCELLED; PENDING_APPROVAL → DRAFT (rejected), CANCELLED, or SENDING **only together with the approval**; SENDING → SENT; SENT and CANCELLED are final. (2) `CHECK (escalate_after_s > 0)`, and `sent_at` frozen once set. (3) `reference` and `created_at` frozen; `rejection_reason` written only on PENDING_APPROVAL → DRAFT; approving moves the campaign to exactly SENDING. (4) `REVOKE UPDATE ON checkin_response FROM nexira_app` (append-only, D-07); a trigger keeps a delivery's `campaign_id`, `person_id`, `channel` and `tenant_id` fixed. | The second re-review of Prompt 18 showed that a campaign sent without approval could be moved back to DRAFT and rewritten, or even re-approved, so the record of what people received could be changed. It also showed that escalation could be disabled, and that check-in answers and deliveries could be edited. "PENDING_APPROVAL → SENDING only with the approval" was added while implementing, because without it a pending campaign could be sent without a second person. | D-31, D-07, MN-05 |
| PC-13 | Proposed; **deferred** by the product owner on 2026-10-26 (PR #20). The dispatcher now sends only deliveries of SENDING campaigns (app fix, tested). This adds the database backstop, so the rule holds even if another sending path appears. | D-31, MN-05 |

## Applied outside the schema file

These are part of migration 0001, but they are not changes to the schema file:

- `REVOKE ALL ON alembic_version FROM nexira_app`. Alembic creates `alembic_version` before the schema runs, so the schema's `GRANT ... ON ALL TABLES` also covered it, and the API could have changed migration state. Tested in `app/tests/test_migrations.py`.

## Cluster bootstrap (outside the schema), awaiting D-29 sign-off

- **`nexira_backup` role** (Prompt 16): `infra/postgres/backup-role.sql` (the role) and `backup-grants.sql` (CONNECT, USAGE, SELECT on the tables and sequences of `public`, and default privileges for tables `nexira_owner` creates later), both included by `init.sql`. LOGIN, BYPASSRLS; no write, create or superuser rights; not `pg_read_all_data`. It exists because FORCE RLS stops `nexira_owner` from running `pg_dump`. It is a role and grants change, not a schema change, so there is no Alembic migration; existing clusters run both files once (`docs/runbooks/backup-restore.md`). Tested in `backend/app/tests/test_backup_role.py`. Review item: `docs/security-review.md` §2.
